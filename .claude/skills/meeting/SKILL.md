# Owner meeting

A session in which a topic is presented to the owner, the owner asks questions, and the owner decides. The chief engineer chairs and presents; agents answer detail questions on request, one at a time; only the owner decides. The agenda of each kind is in `kinds/<kind>.md`.

## 1. Prepare (chief engineer, usually on shift)

1. In the system item's folder: `plm new meeting "<Gate or topic> meeting"`. Set `owner: chief-engineer` in its meta.
2. Fill `kind`, `date` (planned), `agenda` (from `kinds/<kind>.md`, tailored) and `presented` (the IDs to be shown: REV, ANA, DEC, …).
3. Write the artifact `pack.md`, at most about two pages:
   * one-paragraph summary: where the project stands and what the owner must decide;
   * per agenda point the facts, with numbers generated by `plm`, never hand-counted: `plm validate`, `plm suspects`, `plm report coverage --by verification` (and `--allocation`), `plm list findings state:open`, `plm list parameters value:` (TBDs), `plm search … --format json` for lists of items;
   * per decision point: the question, the options with their consequences in numbers, the recommendation and why;
   * the open `needs-owner` issues of the milestone;
   * for gates and status meetings, the risks of `risks.md` that changed.
4. `gh issue create --label meeting --milestone "<milestone>" --title "<MTG-ID> <title> ready"`, the body listing the decisions needed and the path of `pack.md`. Put the issue number in the item's `issue` field.
5. Add the meeting to *Coming owner meetings* in `timeline.md`. `plm validate`, commit, push. End the shift cycle with state `meeting` and the MTG ID in `for_owner`.

The kickoff has no preparation: the owner starts it in a new repository with `/meeting kickoff`.

## 2. Hold (interactive, the owner is present)

1. Check that the shift is not running (skill `chief-engineer`, Session start). Hold the meeting only then.
2. **Open:** the summary of `pack.md` in a few lines. Ask whether to go through the agenda in order or start with a point.
3. **Each agenda point:** present it in at most ten lines, citing IDs with titles. Then wait for questions.
4. **Questions:** answer from the items (`plm show`, `grep`, the scripts' output). For detail, spawn the owning agent with one narrow question. Never invent an answer: what the repository cannot answer becomes an action.
5. **Decision points:** present each one with AskUserQuestion, the recommended option first. The owner may answer with another option. Note the decision, the option chosen and the owner's reason.
6. **Actions:** work that a question or decision needs is not done in the meeting. Note it as an action with an owner agent and a *done when* line.
7. **Close:** read back all decisions and actions. The owner confirms or corrects them.

## 3. Record (right after the meeting, same session)

1. Each decision becomes an item: a `DEC-…` (owner `chief-engineer`, `question`, `alternatives`, `chosen` with the owner's reason, `implements` the requirements it affects), or a change of an owner-constraint requirement by its owner agent.
2. Each action becomes an issue: `gh issue create` with `owner:<agent>`, the milestone and the *done when* line.
3. The MTG item: actual `date`, `decided` (the new DEC IDs), `verdict`, and the artifact `minutes.md`: the questions that changed something, the decisions, the actions with issue numbers. Nothing else.
4. By kind:
   * **Gate go:** set `approved` on the items in scope; open a pull request `develop` → `main` (`gh pr create --base main --head develop --title "<Gate> baseline"`); the owner merges it in the meeting, or tells you to (`gh pr merge <n> --merge --admin`: the owner's account may bypass the review it cannot give its own pull request); then tag `<gate>-baseline` and push the tag; close the GitHub milestone. If the owner merges later, the next owner session tags it.
   * **Go with conditions:** as go, and each condition becomes an issue labelled `gate-condition` on the next milestone.
   * **No-go, rework:** the rework becomes issues on the same milestone; the milestone stays open.
   * **Re-plan:** the owner's new budget and scope go into `timeline.md`.
5. Close the meeting issue and the answered `needs-owner` issues with the commit.
6. Update `timeline.md` (state of the milestone with the MTG ID, next milestone, its budget and entry conditions), `handover.md`, and `project-plan.md` and `risks.md` where the meeting changed them, `plm validate`, commit `MTG-<ID> <title>: <decisions>`, push.
7. Ask the owner whether to start the shift.

## Rules

* The owner's time is the scarce resource: short pack, short answers, one question per decision.
* Present only the current state; history is in git.
* Done topics are not reopened (skill `chief-engineer`, Planning and steering) unless the owner decides so in the meeting.
* Nothing is recorded as decided that the owner did not say.
